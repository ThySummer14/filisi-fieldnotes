# 命令明明找到了 为什么还是不好用

输入“op”，面板同时找到了Open Project和Open Preferences。两个结果都匹配，究竟把谁放第一？若用户此刻想改设置，打开项目就是一次错误选择；若他正在切换工作区，排序又应该相反。单靠字符距离，无法知道这段尚未表达的意图。

命令面板至少要解决候选召回、候选排序与执行三件事。找不到属于召回问题；找到却排很后属于排序问题；已经选中却执行到别处属于交互问题。把它们统一叫作“搜索不够智能”，很难决定该改哪层。

## 模糊匹配并不等于容错拼写

[fzf的算法源码说明](https://github.com/junegunn/fzf/blob/master/src/algo/algo.go)区分较快的首个匹配与寻找更高分位置的算法，并为词边界、连续匹配和字符间隔设置不同影响。用户输入几个首字母时，词边界能提供线索；字符间隔过长又会降低相关性。

该实现中的模糊匹配要求查询字符按顺序出现，并不是自动允许任意拼写错误。输入漏了一个字母与把两个字母交换位置，可能产生不同结果。“fuzzy”这个名字不能替代明确的匹配语义。产品若希望支持错拼、拼音或别名，需要分别实现和验证。

同一个候选字符串可能有多种匹配位置。只找到最早一组字符，未必得到最紧凑或最有意义的那组。[VS Code的fuzzyScorer源码](https://github.com/microsoft/vscode/blob/main/src/vs/base/common/fuzzyScorer.ts)同时维护分数与匹配位置，并考虑连续匹配。高亮应对应实际用于打分的字符，否则用户看到的理由与排序理由不一致。

字面分数本身没有自然的通用单位。某库给80分、另一个给0.9，不能直接混在同一列表比较。把文件搜索、菜单命令与远端文档召回合在一起时，需要校准或分组，避免某个来源因为分值尺度大而永远霸占第一。

## 上下文可以减少噪声 也会藏起功能

[VS Code的命令扩展文档](https://code.visualstudio.com/api/extension-guides/command)区分命令启用条件与菜单显示条件。只有在合适上下文中展示某些命令，可以避免结果被无关项淹没；但如果用户不知道为什么命令消失，也会以为功能根本不存在。

一个只能对选区执行的操作，可以隐藏，也可以显示为不可用并说明“先选择文本”。前者更简洁，后者更利于发现和学习。频繁使用的专业工具未必与新手产品采用同一策略。关键是无结果时能否给出可理解的原因，而不是让用户不断换关键词。

名称也影响召回。“导出”和“另存为”可能在用户心里指同一目标，系统里却是不同命令。别名能连接这些词，但别名不是承诺功能等价。若导出会丢掉编辑信息、保存会保留项目结构，应在结果描述里说明差别，不能只为了提高命中率把二者完全混为一项。

本地化后，英文缩写与中文标题可以并存。已经习惯某个英文命令的用户不必重新学习全部词汇，新用户又能使用界面语言。检索字段可以更丰富，显示标题仍需简短明确。把全部别名都堆进主标题，只会让结果难扫读。

## 排序太勤快 会破坏键盘节奏

最近使用记录能帮助重复任务，但每次结果重排都改变了用户按方向键的路径。如果异步结果刚到就把当前选中项从第二位换成另一条命令，随后按Enter可能执行非预期动作。保持选中项身份，比只保持一个数组索引可靠。

[WAI-ARIA的Combobox模式](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/)描述输入与弹出候选列表之间的键盘交互。命令面板不必机械采用所有组合框变体，但应明确输入焦点、活动候选和最终执行之间的关系。方向键移动候选，不应无声改变输入内容或提前执行高后果动作。

若第一项会根据远端数据不断变化，界面可以先保留本地候选，再以不抢夺当前选择的方式补充结果。加载状态应让人知道列表还可能变化。搜索越快不代表排序越稳定，用户真正感受到的是从输入到确定执行的一整段过程。

破坏性命令尤其不适合只因最近用过就突然跃升。可以给危险动作明确图标或描述，并保留其自身确认流程。命令面板提供快速入口，不应降低动作原有的安全要求。对撤销性差的操作，节省一次按键未必值得。

## 用一次真实选择解释一个分数

排序评估不能只看目标是否出现在前十。常用命令可能要求第一项就对，偶尔使用的命令则更需要容易识别。可以分别记录用户是否继续改词、移动几次选择、是否马上撤销，以及最终执行是否符合目标。单纯提高第一项点击率，也可能只是把默认项做得更醒目。

对开发者，保留一个可解释的调试视图很有帮助：字符匹配分、上下文加权、历史偏好分别贡献多少。这个视图不必展示给所有用户，却能避免“调一个总权重，另一个场景又坏了”的盲试。权重应基于真实任务样例校验，不应假称存在一个所有人共享的最佳排序。

回到Open Project和Open Preferences。输入“op”时并列出现没有问题，标题和类别足以区分；用户再输入“pref”，设置命令就应稳定上升。若他已经用方向键选中Open Project，远端结果随后到达，当前选择仍应指向项目命令。

这组行为没有读心，却让用户能逐步表达意图并保留控制。一个可靠面板可以承认短查询存在歧义，用清楚的候选和稳定的选择消解它；若为了显得聪明而不断抢先重排，字符匹配算法再精细，最后那次Enter仍然可能按错。
