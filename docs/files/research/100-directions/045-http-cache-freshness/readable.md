# 缓存里的新鲜 不等于服务器上的最新

服务器刚把一页内容从版本A改为B，某个浏览器却继续展示A，而且没有发出网络请求。这未必是缓存故障。如果A的响应被允许在十分钟内直接复用，服务器在第二分钟改动内容，并不会隔空收回浏览器手里的许可。

HTTP中的fresh描述响应按缓存策略仍可复用，并不证明源站此刻没有新版本。缓存用年龄与新鲜期判断是否能直接回答，而不是每次先询问源站。省下的那次询问，恰好意味着它可能不知道后来的改动。[RFC 9111](https://www.rfc-editor.org/rfc/rfc9111)把新鲜度、验证和失效分别规定。

## 两个容易看反的名字

`no-cache`允许保存响应，但再次使用前通常需要成功验证；`no-store`要求不存储相应请求和响应。前者的名字很像“什么都别缓存”，实际保留了节省传输正文的机会。若应用只是希望每次先问一下版本有没有变，直接禁止存储可能比所需策略更重。

验证器让缓存能提出一个较便宜的问题。客户端携带旧ETag发起条件请求，服务端判断选定表示是否改变；对符合条件的GET，可返回304而不重传正文。[RFC 9110](https://httpwg.org/specs/rfc9110.html)把ETag定义为不透明验证器，它可以来自版本号或哈希等实现，不要求客户端理解内部格式。

304不是“服务器没处理请求”，也不是一个可以独立显示的空页面。它需要与原有缓存条目结合使用，更新相关元信息后继续复用正文。若某层代理把验证器与错误的表示关联，或者应用变更内容却没有更新验证器，就可能稳定地验证出错误结果。给ETag起了一个漂亮名字不能替代生成规则。

弱验证器还表达了另一层含义：有些变化可以被视为语义等价，但字节并不完全相同。是否允许弱比较，取决于条件请求的用途。把所有ETag当作文件字节的强哈希，会在范围请求等场景中制造错误假设；需要按协议选择适用的比较方式。

## 陈旧响应有时是被允许的

[RFC 5861](https://www.rfc-editor.org/rfc/rfc5861)定义了stale-while-revalidate：响应过期后，在额外窗口内可以先提供旧内容，同时尝试后台验证。它改善等待体验，但用户第一次刷新仍可能看见旧页面。只有后续请求才可能拿到已更新的副本。

用一个示意时间线说明：max-age为60秒，stale-while-revalidate为30秒。忽略传输时间与既有年龄后，70秒到来的请求可能先得到旧内容并触发验证；若一直无人访问到100秒，后台验证并不因时钟走到60秒就必然自动发生。这项策略由请求触发的行为，不能简单理解为一个定时刷新器。

stale-if-error允许在某些错误条件下继续使用旧响应。这可以让故障时的网站仍可阅读，却也需要决定哪些信息可以过时。历史文章正文与刚撤回的访问资格，不能共用同一种陈旧容忍度。协议提供许可，应用负责判断旧答案的后果。

## 同一个URL也可能不是同一份内容

如果服务器根据Accept-Language返回不同语言，只按URL缓存就可能把一种语言交给另一种语言的请求。Vary说明选择表示所依赖的请求头。[MDN的缓存指南](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)以语言协商说明这个问题，也提醒高基数的变化维度会降低缓存复用率。

个人化页面更敏感。响应包含某个人的数据时，必须正确区分私有缓存与共享缓存，不能仅因为请求里有Cookie就假定每一层都会自动安全处理。对认证相关或敏感响应，应核查实际响应头和中间层配置。缓存命中率再高，也不值得冒把甲的数据交给乙的风险。

有些旧内容来自协议缓存之外：应用内查询缓存、Service Worker、自建离线存储都可能独立保留数据。这里没有测试某个框架的默认行为，因此不能用一条通用Cache-Control配置宣称全部解决。诊断时应确认请求究竟在哪层停止，是没有网络请求、边缘缓存回答了，还是源站确实返回了旧数据。

## 更新策略要有完整的依赖关系

静态资源常使用内容指纹文件名：内容变了就改URL，旧文件可以长期缓存。代价是引用这些文件的HTML也需要按合适策略更新；若HTML永久停在旧版本，资源文件再新也不会被请求。部署还应保证新页面引用的文件已经可用，以及旧页面暂时仍能访问旧资源。

对一次“发布后仍旧”的排查，应同时保存URL、响应Date与Age、Cache-Control、ETag、Vary，以及是否发生304。用同一个浏览器的强制刷新得到新内容，只能证明某条路径能取得新版本，不能证明普通访问路径也符合预期。

测试可以把内容明确标成A和B，控制更新时间与第二次请求的间隔，分别经过浏览器和共享缓存。断言应写成“某个窗口内允许A，某个验证后应出现B”，而非笼统的“刷新会更新”。若产品需要更新立即可见，就不能再同时假设客户端可长时间不联系服务器；需要付出验证请求、推送失效或改变URL等成本。

排查时不要先清空全部缓存。清空会消灭能解释错误的年龄、验证器和命中路径，虽然页面暂时好了，下一次发布仍可能复发。先保留一次正常访问的证据，再改变缓存状态，才能比较修复前后。
